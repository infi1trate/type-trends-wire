- The 15-minute wire job only ingests and gives the news desk its turn; the story build and records sweep run in the separate `wire-followups` pass a minute later, which writes its start row, answers its five-second managed caller at once and finishes after the answer through waitUntil (intercepted in `src/server.ts`, route file as inline fallback) inside the host's 30-second after-answer window; slots alternate which step goes first so each gets the whole window every half hour, one pass at a time.
- Story builds run one at a time across instances: each writes its start row, then stands down (finish row "skipped") when an earlier story-build start is under `BUILD_ONE_AT_A_TIME_MS` old or job_runs cannot be read, because overlapping builds from crawler posts and the follow-ups pass coincided with the 23 Nov database outage.
- Every scheduled job asks `standDown()` (jobs/gate.server.ts) first: one anonymous read cut at one second (db-probe.server.ts); a slow database (or safe mode, except for the wire) stands the job down at once with a "skipped: …" run row, because jobs queued behind a slow database during the 23 Nov outage.
- Database health lines, engineering-alert timing and safe mode are pure in `src/lib/db-health.ts` over this instance's probe readings plus the anonymous counts-only `db_load_facts()`; safe mode is per instance (owner switch = newest owner row in service-role `db_safe_mode`, read every 30 s) and its log/alerts are written best-effort once the database answers, because the state must hold while the database is down.
- The records sweep runs one queue (pure `sweepOrder` in records/refresh.server.ts): shared inputs and page models past their limit cheapest first, per-brand sets past their limit, then everything due by closeness to its limit; a held story build makes the sweep go first with 4 s left for the build, because rewriting every due shared input first kept seven kinds 6–14 h past their limits.
